# 엔플랫폼 운영기획서 v4 — 운영관리자 업무 구조 재설계

> 작성 2026-08-19 · 이전 문서(운영기획서-CRUD재설계 v3.x)를 대체한다.
> 원칙: **화면은 업무 단계를 따라간다.** 데이터 테이블이 아니라 운영자가 실제로 처리하는 순서대로 메뉴를 놓는다.

---

## 0. 이 문서를 다시 쓴 이유

기존 관리자 메뉴는 데이터 종류(매각의뢰 / 매입조건 / NDA)로 갈라져 있었다.
그런데 실제 운영은 **접수 → 검증 → 등록 → 노출 → 매칭 → 체결**이라는 한 줄기 흐름이고,
특히 매물이 들어오는 경로가 **두 가지**(직접 등록 / 등록 대행)인데 화면이 하나뿐이라
대행 건을 처리할 자리가 없었다.

핵심 변경 두 가지:

1. **매물 유입 경로를 둘로 분리** — 직접 등록(폼 완비)과 등록 대행(파일만 옴)은 운영 행위가 완전히 다르다.
2. **관리번호는 등록 승인 시점에 생성** — 접수만 된 건에는 번호를 주지 않는다. 번호가 있다는 건 공개 가능한 매물이라는 뜻이다.

## 1. 회원 유형과 매물 유입 경로

| 회원 | 할 수 있는 일 |
|---|---|
| 매각 회원 | ① 매물 **직접 등록** (폼 작성 + 사진·서류 첨부) ② **등록 대행 요청** (채권 관련 파일만 업로드) |
| 매입 회원 | 매입조건 등록 → 자동매칭 열람 → 관심·NDA 요청 |
| 운영관리자 | 회원 승인 · 매물 검증/등록 · 대행 등록 · 매칭 관리 · NDA 승인 |
| 운영파트너 | 위 전 화면 **열람 전용** (수정 불가) |

```
매각 회원 ─┬─ [직접 등록] ─→ 매각의뢰 관리 ─→ 승인 ─→ 관리번호 발번 ─┐
           │                                                          ├─→ 매물관리(공개)
           └─ [대행 요청]  ─→ 매물등록 대행관리 ─→ OCR 파싱 ─→        │
                              운영사 검수·보정 ─→ 등록 ─→ 관리번호 ───┘
```

## 2. 운영관리자 메뉴 구조 (확정)

| # | 메뉴 | 한 줄 정의 | 처리 대상 |
|---|---|---|---|
| 1 | **회원관리** | 가입 신청 자격 검증 → 승인 / 보류 / 거절 | 회원 |
| 2 | **매각의뢰 관리** | 직접 등록된 매물의 폼·첨부 검증 → 등록 승인 | 매물(직접) |
| 3 | **매물등록 대행관리** | 파일만 온 건을 운영사가 대신 등록 (OCR 자동입력 + 검수) | 매물(대행) |
| 4 | **매물관리** | 등록 완료된 전체 매물의 상태·반응·딜 단계 관리 | 매물(공개) |
| 5 | **매입조건 관리** | 매입 회원 매입의향 접수·관리 | 매입조건 |
| 6 | **NPL 매칭 관리** | 매물 ↔ 매입조건 매칭 결과 확인·발송 | 매칭 |
| 7 | **NDA 관리** | 전자서명 접수 → 문서 확인 → 승인 / 거절 | NDA |

> 2·3번은 "등록 전", 4번은 "등록 후"다. 이 경계가 관리번호 유무와 정확히 일치한다.

## 2-1. 사이드바 설계 — 메뉴명 변경안

### 용어 규칙 먼저

이름을 정하기 전에 **말의 규칙**을 세운다. 이게 없으면 메뉴명이 계속 흔들린다.

| 용어 | 뜻 | 언제 쓰나 |
|---|---|---|
| **매각의뢰** | 아직 등록되지 않은 신청 건 | 관리번호 **없음** |
| **매물** | 등록이 확정되어 공개 가능한 건 | 관리번호 **있음** |

> 이 한 줄 규칙만 지키면 "매각의뢰 관리"와 "매물관리"가 왜 다른 메뉴인지 이름만 보고 알 수 있다.

### 변경 대비표

| 현재 메뉴 | 변경 후 | 왜 바꾸나 |
|---|---|---|
| 대시보드 | **대시보드** | 유지 |
| 회원 승인 | **회원관리** | 승인만 하는 곳이 아니다. 차단·복구·이력 조회를 모두 여기서 한다 |
| 매각의뢰 현황 | **매각의뢰 관리** | "현황"은 보기만 하는 느낌. 실제로는 승인·보완요청·거절을 처리한다 |
| — | **매물등록 대행관리** | 신설. 지금 대행 건을 처리할 자리가 없다 |
| (매각의뢰 현황이 겸함) | **매물관리** | 등록 전과 등록 후를 한 화면에서 보던 것을 분리 |
| 매입조건 현황 | **매입조건 관리** | 위와 같은 이유 |
| — | **NPL 매칭 관리** | 신설. 매칭 결과를 보고 발송까지 하는 화면 |
| NDA · 계약 | **NDA 관리** | 계약은 별도 기능이 아니라 NDA 이후 딜 단계다. 이름에서 뺀다 |
| 접수함 | **문의 접수함** | 대행 요청이 전용 큐로 빠지면 여기 남는 건 일반 문의뿐 |
| NPL 수익률 분석 | **수익률 분석** | NPL은 전 메뉴의 전제라 굳이 붙일 필요 없다 |
| 메인 하이라이트 / 언론보도 / 메인 지표 입력 | **메인 하이라이트 / 언론보도 / 메인 지표** | 유지 (입력은 자명해 생략) |

### 사이드바 배치

메뉴를 그룹으로 묶는다. **일이 흘러가는 순서**가 위에서 아래다.

```
운영
  대시보드                    ← 오늘 처리할 일

회원
  회원관리                    ⓷  ← 승인 대기 수

매물
  매각의뢰 관리                ⓶  ← 검토 대기 수
  매물등록 대행관리            ⓵  ← 미처리 대행 요청 수
  매물관리                       ← 등록 완료 (배지 없음)

거래
  매입조건 관리
  NPL 매칭 관리
  NDA 관리                    ⓹  ← 검토 대기 수

지원
  문의 접수함                  ⓸  ← 미처리 문의 수
  수익률 분석

콘텐츠
  메인 하이라이트
  언론보도
  메인 지표
```

**배지 규칙** — 숫자 배지는 **내가 지금 처리해야 하는 것**에만 붙인다.
매물관리·매입조건 관리처럼 "쌓여 있는 것을 보는" 화면에는 붙이지 않는다.
배지가 아무 데나 붙으면 아무 의미가 없어진다.

**그룹을 나눈 이유** — 메뉴가 12개다. 평평하게 늘어놓으면 찾는 데 시간이 걸린다.
`회원 → 매물 → 거래`는 실제 업무가 진행되는 순서이므로, 운영자는 위에서 아래로 훑으면 된다.

## 3. 메뉴별 상세

### 3-1. 회원관리

**목적** — 승인제 플랫폼의 관문. 자격이 검증된 회원만 서비스에 들어온다.

| 항목 | 내용 |
|---|---|
| 목록 열 | 이름 · 회사 · 유형(매각/매입/겸용) · 연락처 · **연동 데이터(매물 n · 조건 n · NDA n)** · 가입일 · 상태 · 관리 |
| 첨부 검증 | 명함, 사업자등록증 — 상세 패널에서 이미지로 즉시 확인 |
| 상태 | 승인대기 → **승인** / **보류**(사유 필수) / **거절** · 활성 → **차단** · 거절·탈퇴 → **복구** |
| 승인 효과 | 로그인 허용 + 그 회원 Key로 이후 모든 업무 데이터가 연결됨 |

**규칙**

- 상태 전이는 가능한 것만 노출한다. 불가능한 버튼은 띄우지 않는다.
- 보류는 사유를 남기고 회원에게 통지한다.
- 연동 데이터 배지를 누르면 해당 목록이 **그 회원 기준**으로 열린다 (`?user=<회원ID>`).

---

### 3-2. 매각의뢰 관리 — 직접 등록 건

**목적** — 매각 회원이 스스로 채운 폼이 **공개 가능한 수준인지** 검증하고 등록을 승인한다.

**운영자가 확인하는 것**

| 구분 | 확인 항목 |
|---|---|
| 등록 폼 | NPL 세부내역 표준 40필드 — 필수 누락 여부 |
| 사진 | 담보물 사진 (최소 1장 권장) |
| 참고 파일 | 감정평가서 · 채권 관련 서류 · 등기부 등 |
| 회원 | 등록한 매각 회원(기관명) — 클릭 시 회원 상세 |

**상태 흐름**

```
접수(검토대기) ──[보완요청]──→ 보완대기 ──(회원 수정)──→ 접수
      │
      ├──[승인]──→ 등록완료   ★ 이 시점에 관리번호(N26-n) 자동 발번 → 매물관리로 이동
      └──[거절]──→ 거절 (사유 기록 · 회원 통지)
```

**규칙**

- 승인 전까지는 운영자와 매각 회원 **모두** 내용을 수정할 수 있다. 승인 후 수정은 운영자만.
- 삭제는 잘못 접수된 건에만 쓴다. 이력을 남겨야 하면 거절을 쓴다.
- **관리번호는 승인 순간 발번한다.** 접수 단계에는 번호가 없다(임시 접수번호로 식별).

#### 보완요청 (확정 · 2026-08-19)

거절과 보완요청은 다르다. **거절은 끝내는 것이고, 보완요청은 이어가는 것**이다.
자료가 조금 모자란 건을 거절하면 회원은 처음부터 다시 올려야 한다. 그래서 중간 상태를 둔다.

| 항목 | 내용 |
|---|---|
| 운영자 화면 | `[승인]` `[보완요청]` `[거절]` 3개 버튼 |
| 보완요청 입력 | **부족한 항목 체크 + 한 줄 사유** (예: 감정평가서 누락 / 담보물 사진 없음) |
| 회원에게 | 알림함 + 이메일 통지, 어떤 항목이 부족한지 그대로 전달 |
| 회원 화면 | 해당 건이 `보완 필요`로 표시되고, 지적된 항목이 폼에서 강조된다 |
| 재제출 | 회원이 수정·저장하면 자동으로 `접수` 상태로 복귀 → 운영자 큐에 다시 뜬다 |
| 이력 | 보완요청 횟수와 사유를 남긴다 (반복되면 운영자가 직접 연락할 판단 근거) |

```
접수 ──[보완요청]──→ 보완 필요 ──(회원 수정·재제출)──→ 접수 ──[승인]──→ 등록완료
```

### 3-3. 매물등록 대행관리 — 대행 요청 건

**목적** — 매각 회원이 **파일만** 올렸을 때 운영사가 대신 등록한다. 이 화면이 없어서 지금은 처리할 자리가 없다.

#### 3-3-0. 접수 경로 — 하나의 입구, 두 갈래 (확정)

매각 회원에게 "매각의뢰"는 하나의 행위다. 메뉴를 둘로 나누면 무엇을 골라야 할지 모른다.
그래서 **입구는 `NPL 매각의뢰` 하나로 두고, 폼 첫 화면에서 방식을 고르게 한다.**

```
[NPL 매각의뢰] 클릭
        ▼
 ┌──────────────────────────────────────────────┐
 │ 어떻게 등록하시겠습니까?                       │
 │                                              │
 │ ○ 직접 등록                                   │
 │   폼을 작성하고 사진·서류를 첨부합니다          │
 │   → 소요 10~15분 · 등록이 빠릅니다             │
 │                                              │
 │ ○ 등록 대행 요청   ← 파일만 있으면 됩니다       │
 │   가지고 계신 채권 파일만 올려주세요            │
 │   운영사가 내용을 정리해 등록해 드립니다        │
 │   → 소요 1분 · 영업일 1~2일 내 등록            │
 └──────────────────────────────────────────────┘
        │                        │
   기존 등록 폼            파일 업로드 + 연락처만
        ▼                        ▼
  매각의뢰 관리 (3-2)      매물등록 대행관리 (3-3)
```

**왜 이 방식인가**

| 대안 | 판단 |
|---|---|
| 접수함(1:1 문의)으로 받기 — 현재 방식 | ✗ 문의와 섞여 큐가 흐려지고, 파일 여러 개·진행 상태·OCR 결과를 담을 그릇이 없다 |
| 전용 메뉴를 따로 신설 | ✗ 회원이 두 메뉴 중 무엇을 눌러야 할지 판단해야 한다. 이탈 지점이 생긴다 |
| **한 입구 + 폼 첫 단계 분기** | ✓ 회원은 고민 없이 들어오고, 운영자에게는 두 개의 큐로 갈라져 도착한다 |

**대행 요청 폼에서 받는 것 (최소화)**

| 항목 | 필수 | 비고 |
|---|---|---|
| 파일 업로드 | ✓ | 복수 첨부 — 채권원장·감정평가서·등기부·엑셀 템플릿 등 |
| 담당자 연락처 | ✓ | 회원 정보에서 자동 채움 (수정 가능) |
| 간단 메모 | — | "급매 희망" 같은 한 줄 |

> 그 외에는 **묻지 않는다.** 물어볼 수 있었으면 직접 등록을 골랐을 것이다.

**저장 위치 — 접수함이 아니라 전용 테이블**

파일 여러 개 · 진행 상태 · OCR 파싱 결과를 함께 들고 있어야 하므로 지원 티켓으로는 부족하다.

```
listing_intakes                          -- 등록 대행 접수
  id · seller_id · status · memo · contact
  files[]           (경로 · 원본파일명 · 종류)
  parsed_draft      (OCR 파싱 결과 jsonb — 운영자 검수 전 초안)
  listing_id        (등록 확정 시 연결)
  created_at · registered_at · registered_by

status: 접수 → 파싱완료 → 검수중 → 등록완료 / 반려
```

기존 `support_tickets` 로 들어온 대행 성격의 건은 이 테이블로 옮겨 담는다(1회성 이관).

#### 3-3-1. 처리 순서 — 화면 하나에서 4단계

| 단계 | 화면 | 운영자 행위 |
|---|---|---|
| ① 파일 확인 | 회원이 올린 원본 파일 목록 + 뷰어 | 채권정보 파일 · 엑셀 템플릿 · 감정평가서 열람 |
| ② 자동 파싱 | **[OCR 자동입력]** 버튼 | 파일 → NPL 세부내역 폼에 자동 기입 |
| ③ 검수·보정 | 세부내역 폼 (파싱값 하이라이트) | 잘못 들어간 값 수정, 빠진 값 보완 |
| ④ 등록 | **[등록 확정]** | 매물 생성 + **관리번호 자동 발번** → 매물관리로 이동 |

**이미 있는 자산 (그대로 재사용)**

- `POST /api/v1/ocr/parse-template` — 매물등록 엑셀 템플릿 v3 → 세부내역 폼 자동 매핑 (기본정보 / 특수조건 18항목 / 필요서류 25항목)
- `POST /api/v1/ocr/autofill`, `POST /api/npl/ocr` — 이미지·PDF OCR
- `POST /api/v1/admin/listings/from-ticket` — 접수 건을 매물로 전환하며 **seller_id를 요청 회원으로 연결**

**규칙**

- 파싱 결과는 **반드시 운영자 확인을 거친다.** 자동 등록은 하지 않는다.
- 어떤 값이 OCR에서 왔고 어떤 값을 사람이 고쳤는지 화면에서 구분해 보여준다.
- 대행 등록된 매물의 소유자는 **요청한 매각 회원**이다. 운영사가 아니다.

#### 3-3-2. 등록 확정 방식 — 바로 등록 (확정 · 2026-08-19)

운영사가 검수를 마치면 **회원 확인을 기다리지 않고 바로 등록한다.**
대행을 요청한 이유가 "손이 가는 걸 맡기려는 것"인데 다시 확인을 요구하면 대행의 의미가 없다.

다만 내용이 잘못 등록될 위험은 남으므로, 확인을 **사전 승인 대신 사후 통지**로 옮긴다.

| 시점 | 처리 |
|---|---|
| 등록 확정 즉시 | 매각 회원에게 **알림함 + 이메일** 통지 — "N26-42 로 등록되었습니다" |
| 통지 내용 | 관리번호 · 핵심 항목 요약(소재지·채권액·감정가) · **[내용 확인하기]** 링크 |
| 회원 화면 | 내 매물에서 전체 내용 확인, 틀린 부분은 **[수정 요청]** |
| 수정 요청 | 운영자 큐로 즉시 도착 → 운영자가 고쳐 반영 |

> 즉, **먼저 등록하고 곧바로 알린다.** 회원은 승인 절차 없이도 내용을 통제할 수 있다.

**안전장치** — 등록 확정 직전 화면에 필수 항목 누락을 경고한다(소재지·채권액·감정가·담보유형).
누락 상태로도 등록은 가능하되, 매물관리에서 `보완 필요` 표시가 붙는다.

### 3-4. 매물관리 — 등록 완료 매물

**목적** — 공개된 매물의 상태·반응·진행을 한 화면에서 본다.

| 열 | 내용 |
|---|---|
| 관리번호 | N26-n (클릭 → 세부내역) |
| 등록일자 | 등록 확정일 |
| 매각 회원(기관명) | 클릭 → 회원 상세 / "이 회원만 보기" |
| 지역 · 유형 · 채권액 | 매물 기본 정보 |
| NPL 상태 | 진행중 / 협의중 / 매각완료 |
| **딜 진행 단계** | 그 매물에서 **가장 앞선 단계** + `외 n건` (단계는 NDA 건별 관리) |
| **관심 등록 수** | 하트 수 |
| **NDA 체결 수** | 승인된 NDA 수 / 전체 요청 수 |
| 마케팅 | 운영사 내부 채널 진행 표시 |

**보기 전환** — [건별] / [회원별]. 회원별은 매각 회원을 앞에 한 번만 두고 그 회원의 매물을 옆에 나열한다.

### 3-5. 매입조건 관리

**목적** — 매입 회원의 매입의향을 접수하고, 그 조건으로 매칭을 돌린다.

| 열 | 내용 |
|---|---|
| **매입 회원 · 연락처** | 첫 열 (클릭 → 회원 상세) |
| 등록일 · 우선순위 | |
| 담보유형 · 지역 · 면적 · 금액대 | 매입조건 등록 폼과 **1:1 동일 필드** |
| 요청사항 | 자유 기재 |
| **매칭 건수** | 이 조건에 맞는 현재 매물 수 (클릭 → 매칭 관리) |

**규칙** — 매입조건은 **비공개 데이터**다. 목록 조회 기본값은 본인 것이고, 전체 조회는 운영자만 가능하다.

### 3-6. NPL 매칭 관리 — 신규 설계 제안

> "어떻게 해야 할지 모르겠다"고 하신 부분입니다. 구조를 제안합니다.

**문제 정의**

매칭 점수는 이미 계산된다 (담보유형 35 + 지역 25 + 금액대 20 + 등급 10 + 긴급도 10 = 100점).
없는 것은 **계산 결과를 가지고 운영자가 무엇을 하는가**이다.
그래서 매칭 관리는 조회 화면이 아니라 **발송·성과 화면**으로 만든다.

**핵심 원칙 — 매칭은 자동, 발송은 수동**

플랫폼 철학이 "공개하지 않는 것이 기능"이므로 매칭됐다고 자동 통지하지 않는다.
운영자가 확인하고 **골라서 보낸다.** 화면은 그 판단을 돕는 도구다.

```
매칭 계산(자동) → 후보 목록 + 점수 → 운영자 선별 → 발송 → 반응 추적
                                        ↑
                            여기가 매칭 관리 화면의 존재 이유
```

**세 개의 탭**

| 탭 | 보는 단위 | 운영자가 하는 일 |
|---|---|---|
| ① 매물 기준 | 매물 1건 | "이 매물을 원할 만한 매입 회원" 목록(점수순) → 선별 발송 |
| ② 회원 기준 | 매입조건 1건 | "이 회원 조건에 맞는 매물" 목록 → 1:1 리스트 제안 |
| ③ 발송 이력 | 발송 1건 | 언제 · 누구에게 · 무엇을 보냈고 → 열람/관심/NDA로 이어졌는가 |

**① 매물 기준 탭 — 화면 예시**

```
관리번호 N26-12 · 서울 강남구 오피스 · 채권액 45억
──────────────────────────────────────────────────────────────
□  92점  ㈜한국인베스트 · 박매입   지역○ 유형○ 금액○   [발송]
□  78점  트러스트파트너스 · 김자산  지역○ 유형○ 금액△   [발송]
■  61점  최자산                    지역○ 유형△ 금액○   발송됨 (08-17)
                                            [선택 2건 일괄 발송]
```

- 점수 옆에 **왜 매칭됐는지**를 한 줄로 표시한다 (지역○ 유형○ 금액△).
- 이미 보낸 회원은 `발송됨 (날짜)`로 표시해 중복 발송을 막는다.
- 회원명 클릭 → 회원 상세(연락처 · 이력).

**③ 발송 이력 탭 — 성과 측정**

| 발송일 | 관리번호 | 받은 회원 | 열람 | 관심 | NDA | 결과 |
|---|---|---|---|---|---|---|
| 08-17 | N26-12 | ㈜한국인베스트 | O | O | 승인 | 협의중 |
| 08-17 | N26-12 | 트러스트파트너스 | O | — | — | — |

이 표가 쌓이면 "어떤 조건의 회원에게 어떤 매물을 보내면 반응이 오는가"를 데이터로 알 수 있다.

**발송 수단 — 알림함 + 이메일 (확정 · 2026-08-19)**

둘 다 보낸다. 알림함만으로는 접속하지 않는 회원에게 닿지 않고, 이메일만으로는 서비스 안에서 흐름이 끊긴다.

| 수단 | 역할 | 내용 |
|---|---|---|
| 알림함 | 서비스 안에서의 동선 | 관리번호 · 지역/유형/금액대 요약 · **[매물 보기]** |
| 이메일 | 도달률 | 같은 요약 + 로그인 링크 |

- 이메일에는 **채권기관·담당자 정보를 절대 넣지 않는다.** 지역·유형·금액대까지만 담는다(공개 범위 §3-7 준수).
- 발송 실패(반송·미수신)는 이력에 남겨 운영자가 다른 경로로 연락할 수 있게 한다.
- 한 회원에게 짧은 기간 다수 매물이 매칭되면 **묶어서 하루 1회**로 보낸다(스팸 방지).

**필요한 신규 데이터**

```
match_dispatches
  id · listing_id · demand_id · user_id · score · sent_at · sent_by
  channel           (알림함 / 이메일 / 둘 다)
  email_status      (발송 · 반송 · 열람)
  opened_at · favorited_at · nda_requested_at      ← 반응 추적
```

**단계적 도입 제안** — 한 번에 다 만들지 않는다.

1. **1순위** — ① 매물 기준 탭 + 발송. 지금 바로 쓸 수 있다.
2. **2순위** — ③ 발송 이력 + 반응 추적. 데이터가 쌓여야 의미가 생긴다.
3. **3순위** — 점수 가중치 조정 UI. 실제 반응 데이터를 본 뒤에 손대는 게 맞다.

### 3-7. NDA 관리

**목적** — 전자서명 접수 → 문서 확인 → 승인 / 거절. **NDA 요청 1건이 1행**이다.

**흐름**

```
매입회원 전자서명 제출
      │  ← 이 시점에 NDA 전문이 확정·보관된다 (약관이 바뀌어도 체결본은 불변)
      ▼
운영사 검토 ──[승인]──→ 세부내역 열람 오픈 + 회원 통지
      └──────[거절]──→ 사유 통지
```

**화면 구성**

- 상단: **전체 / 검토 대기 / 승인 / 거절** 건수 — 누르면 그 상태만 조회
- 검색: 관리번호 · 요청 회원 · 매각 회원 · 단계
- 행: 관리번호 · 매물/매각회원 · **요청 회원** · 요청일 · 상태 · **딜 진행 단계(건별)** · **[문서]**
- **[문서]** → NDA 전문 뷰어: PDF 저장 / PDF 보관 / 보관본 열기 (보관 삭제는 운영자만)

**공개 범위**

| 정보 | NDA 승인 전 | NDA 승인 후 | 협의 단계 |
|---|---|---|---|
| 지역 · 유형 · 금액대 | 공개 | 공개 | 공개 |
| 세부주소 · 서류 · 상세 | 비공개 | **공개** | 공개 |
| **채권기관명** | 비공개 | **비공개** | 운영사 통해 공유 |
| **담당자 성명 · 직책 · 연락처** | 비공개 | **비공개** | 운영사 통해 공유 |

> NDA를 체결해도 채권기관과 담당자 정보는 공개하지 않는다. NDA 전문 제4조에 명문화되어 있다.

## 6. 현재 구현 대비 갭

| 메뉴 | 현재 상태 | 필요 작업 |
|---|---|---|
| 사이드바 | 평평한 12개 | **그룹화 + 메뉴명 변경 + 처리 대기 배지** (§2-1) |
| 회원관리 | 있음 (이름: 회원 승인) | 이름 변경 |
| 매각의뢰 관리 | 매물관리와 섞여 있음 | **승인 전/후 분리**, 보완요청 상태, 첨부 검증 UI |
| 매물등록 대행관리 | **없음** | **신규** — 접수 폼 분기 + `listing_intakes` + 파일 뷰어 + OCR 자동입력 + 검수 + 등록 확정 |
| 매물관리 | 부분 | 관심 수 · NDA 수 열 추가 (딜 단계는 반영 완료) |
| 매입조건 관리 | 있음 | 매칭 건수 열 추가 |
| NPL 매칭 관리 | 계산만 있음 | **신규** — 발송 화면 + `match_dispatches` + 알림/이메일 발송 + 반응 추적 |
| NDA 관리 | 재편 완료 | 이름 변경 (NDA·계약 → NDA 관리) |

**개발 우선순위 제안**

| 순서 | 작업 | 왜 이 순서인가 |
|---|---|---|
| 1 | 매각의뢰 등록 폼 **분기** + `listing_intakes` | 대행 요청이 들어올 통로부터 열어야 한다 |
| 2 | **매물등록 대행관리** 화면 (파일 뷰어 → OCR → 검수 → 등록) | 지금 처리할 자리가 아예 없다 |
| 3 | 매각의뢰 관리 **분리** + 보완요청 | 등록 전/후 경계를 화면으로 확정 |
| 4 | 사이드바 **그룹화 + 메뉴명 변경** | 위 화면들이 생긴 뒤 한 번에 정리 |
| 5 | 매물관리 열 보강 (관심 수 · NDA 수) | 표시 항목 추가 — 가볍다 |
| 6 | NPL 매칭 관리 ① 매물 기준 탭 + 발송 | 여기부터 새 가치 |
| 7 | 매칭 발송 이력 · 반응 추적 | 데이터가 쌓여야 의미가 생긴다 |

> 4번(메뉴명 변경)을 뒤로 둔 이유 — 화면이 없는 상태에서 이름만 바꾸면 빈 메뉴가 생긴다.
