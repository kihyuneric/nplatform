# 엔플랫폼 운영기획서 v3.1 — 제로베이스 CRUD 재설계

> **최종 갱신 2026-08-19** (초안 2026-08-18) — 기존 개발에 결합되지 않은 백지 설계.
> 2026-08-19 추가: §4-2-1 겸용 회원 구성 · §5-1 회원 승인 버튼 규칙 · §6-1 회원 Key 연결 원칙 ·
> §6-2 콘텐츠 이미지 첨부 · §6-3 매각 화면 마케팅 제외.
> 접근: 서비스는 **5개 핵심 데이터** 위에서 돌아가고, 모든 화면(서비스·마이페이지·관리자)은
> 그 데이터에 대한 **CRUD(생성·조회·수정·삭제)의 조합**일 뿐이다.
> 이 문서에 없는 화면·기능·데이터는 만들지 않는다. 재개발 시 이 문서가 유일한 기준.

---

## 0. 설계 원칙

1. **데이터가 먼저, 화면은 나중** — 화면은 "누가 어떤 데이터를 CRUD 하는가"로만 정의한다.
2. **하나의 데이터에 하나의 폼** — 같은 데이터를 만지는 화면이 두 개면 하나는 잘못된 것이다.
3. **회원이 만든 것은 회원 화면에, 운영자가 만든 것은 관리자 화면에** — 그리고 서로의 결과가 상대 화면에 실시간으로 보인다(연동).
4. **필수만** — 정산·티어·크레딧·등급·분석리포트·커뮤니티·딜룸은 서비스에 없다. 어떤 화면에도 두지 않는다.

## 1. 핵심 데이터 5 + 운영 콘텐츠 1

| # | 데이터 | 정의 | 생명주기(상태) |
|---|---|---|---|
| E1 | **회원** Member | 계정 + 역할(매각/매입, 겸용 가능) + 승인 상태 | 승인대기 → 활성 / 보류(사유) / 거절 / 차단 / 탈퇴 |
| E2 | **매물** Listing | 매각의뢰로 생성되는 NPL 물건 (표준 40필드 + 관리번호 N-XX) | 검토대기 → 공개(진행중 → 협의중 → 매각완료) / 거절 / 종료 |
| E3 | **매입조건** Demand | 매입 회원의 매칭 기준 (지역·유형·금액대·우선순위) | 활성 / 삭제 |

| E6 | 운영 콘텐츠 | 메인 히어로 · 하이라이트 8 · 언론보도 · 지표 9종 | 관리자 CRUD 전용 |

파생 데이터(별도 화면 없음): 마케팅 진행(E2에 종속: 8채널 체크·상담수·딜단계·매칭일), 관심(E2×회원 북마크), 문의 티켓(접수함으로만).

|---|---|
| 회원가입 | E1.C (역할 선택 매각/매입 → 매입은 법인/개인 분기, 완료 시 매입조건 폼으로 이동) |

| 메인 / 소개 | E6.R |

### 4-2-1. 겸용 회원(매각+매입)의 마이페이지 구성 (2026-08-19 명시)

한 회원이 두 역할을 모두 가지면 **화면을 새로 만들지 않고 합집합으로 구성**한다.

| 요소 | 매각 단독 | 매입 단독 | **겸용** |
|---|---|---|---|
| 좌측 메뉴 | 대시보드 · 내 매물 · 알림센터 · 설정 | 대시보드 · 매입 조건 · 관심매물 · 알림센터 · 설정 | **대시보드 · 내 매물 · 매입 조건 · 관심매물 · 알림센터 · 설정** (합집합) |
| 대시보드 요약 블록 | (내 매물 화면의 주간 활동 요약) | 이번 주 브리핑 (매입) | **매각 주간 활동 요약(골드) + 매입 이번 주 브리핑(블루) 2개 병행** |
| 요약 카드 | 내 매물 · 알림센터 · 설정 | 매입 조건 · 관심매물 · NDA 진행 | **내 매물 + 매입 조건 · 관심매물 · NDA 진행** |
| 하단 CTA | NPL 매각의뢰 | NPL 자동매칭 | NPL 자동매칭 (매각의뢰는 내 매물에서) |

- 역할 판정은 **users.roles 배열**(DB)이 기준 — 관리자가 역할을 추가하면 다음 진입부터 즉시 합집합으로 바뀐다.
- 겸용 회원은 자기 매물의 반응(관심·NDA·상담)과 자기 매입조건의 매칭을 **한 화면에서 동시에** 본다.
- 알림도 두 종류를 모두 수신한다: 일일 다이제스트(매입) + 주간 리포트(매각).

### 4-3. 관리자 — 데이터당 화면 1개 + 콘텐츠 + 접수함

| 화면 | = 데이터 × CRUD |
|---|---|
| 대시보드 `/admin` | 전 데이터 카운트 R (승인대기 N·검토대기 N·NDA 검토 N·오늘 접수 N) — 각 숫자는 해당 화면으로 클릭 이동 |
| 회원 승인 `/admin/users` | E1.R·U — 목록(검색·필터·페이징) + 상세 모달(첨부 뷰어·NDA/매입조건 이력·역할 관리·보류·비번초기화·탈퇴) |
| 매각의뢰 현황 `/admin/listings` | E2.R·U·D — 검토승인/거절 + 세부내역(40필드) 패널 + 마케팅 패널(8채널·상담·딜단계·매칭일) |
| 매입조건 현황 `/admin/demands` | E3.R |
| NDA · 계약 `/admin/agreements` | E4.R·U (승인/거절 → 즉시 매입회원 열람 해제 + 알림) |

| 콘텐츠 4종 `/admin/highlights·press·main-stats(+히어로)` | E6.C·R·U·D ↔ 메인 즉시 반영 |

파트너: 위 관리자 화면 전부 R 전용 (입력 비활성 + 배너).

## 5. 상태 기계 — 전이는 정해진 주체만

```
E1 회원   승인대기 ─관리자─> 활성 | 보류(사유) | 거절        활성 ─관리자─> 차단 | 탈퇴
          거절·탈퇴 ─관리자─> 활성(복구)
E2 매물   검토대기 ─관리자─> 공개 | 거절
          공개: 진행중 ─매각회원/관리자─> 협의중 ─> 매각완료
          공개 ─매각회원 요청 + 관리자 승인─> 종료
E4 NDA    제출 완료(매입회원) ─관리자─> 승인 | 거절
```

상태를 바꾸는 순간 = 알림 발생 지점 (아래 6).

### 5-1. 회원 승인 화면의 버튼 규칙 (2026-08-19 확정)

**현재 상태에서 가능한 전이만 버튼으로 노출한다.** (없는 버튼 = 불가능한 전이)

| 현재 상태 | 노출 버튼 | 결과 |
|---|---|---|
| 승인대기 · 보류 | **[승인]** **[거절]** | 활성 / 거절 |
| 활성 | **[차단]** | 차단 (로그인·이용 중지) |
| 거절 · 탈퇴 · 차단 | **[승인(복구)]** | 활성 |

- 어느 상태에서든 **[상세]** 는 항상 노출 — 첨부·이력 확인 후 보류(사유 메모)·비밀번호 초기화·탈퇴 처리 가능.
- 상태 배지: 승인대기(주황) · 보류(진주황, 사유 표시) · 활성(초록) · 거절(빨강) · 차단/탈퇴(회색).
- 거절·차단·탈퇴는 되돌릴 수 있어야 하므로 승인(복구) 경로를 항상 남긴다.

## 6. 알림 = 상태 전이의 기록 + 요약 발송

| 트리거 | 수신자 | 채널 |
|---|---|---|
| E1 승인/거절/보류 | 해당 회원 | 인앱+메일 |
| E4 제출 | 매물 소유 매각 회원 + 관리자 | 인앱 |
| E4 승인/거절 | 요청 매입 회원 | 인앱+메일 |
| 일일 다이제스트 (신규 매칭 N + 하이라이트 ≤2 + `?alert=` 링크) | 활성 매입 회원 | 인앱+메일 (매일 08시) |
| 주간 리포트 (NDA +7일·관심·상담) | 활성 매각 회원 | 인앱+메일 (월 08시) |

수신 설정(설정 화면)이 발송을 필터한다. 그 외 알림은 만들지 않는다.

## 6-1. 회원 Key 연결 원칙 (2026-08-19 추가)

**모든 업무 데이터는 회원 아이디(user_id)로 연결되고, 리스트 어디서든 한 번의 클릭으로 회원 정보에 도달한다.**

| 리스트 | 클릭 지점 | 열리는 것 |
|---|---|---|
| 매입조건 현황 | 담당자(등록 회원) | 회원 상세 패널 — 연락처·회사·상태 + 매입조건·NDA·관심·매물·문의 이력 |
| 매각의뢰 현황 | 매물명 아래 "매각 ○○○" | 〃 (매각 회원) |
| NDA · 계약 | NDA 요청자 이름 | 〃 (요청 매입 회원) |
| 회원 승인 | 상세 버튼 | 〃 (+ 승인·보류·거절·역할·비번초기화·탈퇴) |

- 판정·조인 기준은 **user_id**, 이메일은 구 데이터 폴백으로만 사용한다.
- 회원 상세 패널(`components/admin/member-pane.tsx`)은 4개 화면이 공유한다 —
  화면마다 다른 회원 뷰를 만들지 않는다.
- 매각의뢰 접수 → **매물 전환** 시 접수 회원이 `seller_id`로 연결된다 (접수함 액션).
- 관심매물은 서버(`user_favorites`)에 회원별로 저장된다 (기기 무관·운영자 추적 가능).

### 6-1-1. 회원 → 데이터 (역방향 연결 · 2026-08-19 확정)

회원 승인이 끝나면 그 회원 아이디가 **모든 업무 데이터의 Key**가 된다.
운영자는 "이 회원이 무엇을 갖고 있는지"를 회원 목록에서 바로 보고, 클릭 한 번으로 그 목록만 볼 수 있어야 한다.

| 화면 | 표시 | 이동 |
|---|---|---|
| 회원 승인 목록 | `연동 데이터` 열 — 매물 N · 조건 N · NDA N 배지 | 배지 클릭 → 해당 목록을 **이 회원 기준**으로 조회 |
| 회원 상세 패널 | 섹션 헤더 우측 "매각의뢰 현황 / 매입조건 현황 / NDA·계약" 링크 | 〃 |

- 공통 규약: `?user=<회원ID>` — 세 목록 화면(`/admin/listings`, `/admin/demands`, `/admin/agreements`)이 모두 지원한다.
- 필터 적용 시 상단에 **회원 기준 바**(회원명 · 건수 · [필터 해제])를 띄운다 (`components/admin/member-filter-bar.tsx`).
- 매각의뢰 현황은 서버 쿼리(`seller_id`)로, 매입조건 현황은 `user_id`로 좁힌다.
- NDA·계약은 **양방향** — 그 회원이 매각 회원인 매물 + 그 회원이 NDA를 요청한 매물을 함께 보여준다.
- 목록 첫 열은 항상 **회원**이다: 매입조건 현황 = 매입 회원(회사 · 이름 + 연락처),
  NDA·계약 = 매각 회원, 매각의뢰 현황 = 매물명 아래 매각 회원.
- NDA 요청자 집계는 `listing_marketing.nda_requests[].user_id` 를 소스로 한다
  (`nda_agreements` 테이블은 미사용).

### 6-1-2. 관리번호 (2026-08-19 확정)

형식 **`NPL{연도 2자리}-{연도별 등록순}`** — 예) `NPL26-1`, `NPL26-2` … 0 패딩 없음.

- 저장 위치: `npl_listings.listing_no` (등록 시 트리거 `assign_listing_no` 가 자동 채번 · 유니크 인덱스)
- 화면 공통 함수: `lib/listing-no.ts` `buildListingNoMap()` — DB 값이 있으면 **무조건 그 값**을 쓰고,
  샘플·미채번 건만 연도별 최대값 다음 번호로 이어 붙인다.
- 따라서 같은 매물은 자동매칭 · NDA·계약 · 매각의뢰 현황 어디서 보든 **번호가 같다**.
- 메인 하이라이트(`main_highlights.no`)도 같은 형식을 쓴다.

## 6-2. 관리자 콘텐츠 이미지 (2026-08-19 추가)

메인 하이라이트 · 언론보도 · 히어로 카드의 이미지는 **URL 붙여넣기와 파일 직접 첨부 둘 다** 지원한다.
- 공용 입력기: `components/admin/image-input.tsx` (미리보기 + URL 입력 + [파일 첨부])
- 업로드: Supabase Storage `content-images` 버킷 → 공개 URL 자동 입력 (JPG·PNG, 5MB 이하)

## 6-3. 매각 회원 화면에서 제외 (2026-08-19)

마케팅 8채널 체크리스트(땅집고옥션·엔플랫폼 채널별 진행 표시)는 **매각 회원 화면에서 제거**한다.
매각 회원에게 중요한 것은 **관심 · NDA 요청 · 상담 진행 · 딜 단계**다.
(채널 체크는 운영자 내부 관리 화면에서만 유지)
